BUG #1 — CRITICAL (WILL CRASH OR PRODUCE NaN)
File: src/models/cnn_encoder.py, line 147
What: Conv2d kernel_size=(2,1) assumes ResNet output height is EXACTLY 2.
      But the actual ResNet-18 stride math gives a DIFFERENT height.

      Let's trace through for input [B, 3, 64, 512]:
        conv1:    stride=2  → H=32, W=256
        bn1/relu: no change
        maxpool:  stride=(2,2) → H=16, W=128
        layer1:   stride=1  → H=16, W=128
        layer2:   stride=2  → H=8,  W=64   (layer2's first block has stride=2)
        layer3:   stride=(2,1) [patched] → H=4, W=64
        layer4:   stride=(2,1) [patched] → H=2, W=64

      OK so H=2 is correct for the default case (high_res_temporal=False).
      
      BUT for high_res_temporal=True:
        maxpool:  stride=(2,1) → H=16, W=256   (not 128!)
        layer2:   stride=2  → H=8, W=128
        layer3:   stride=(2,1) → H=4, W=128
        layer4:   stride=(2,1) → H=2, W=128
      
      H=2 still holds. Conv2d(kernel=(2,1)) will output H=1. OK.
      
      HOWEVER: layer2 is NOT patched! layer2 still has its ORIGINAL
      ResNet-18 stride of 2 on BOTH axes: stride=(2,2).
      This means width goes 128→64 in the default case, which is correct.
      
      ACTUAL STATUS: H=2 is correct. Conv2d(2,1) is safe. NO CRASH.
      
      BUT: width_downsample is WRONG for high_res_temporal=True!
      With high_res_temporal=True:
        conv1: W/2, maxpool: W/1, layer2: W/2 → total W/4
        So width_downsample should be 4. Code says 4. CORRECT.
      
      With high_res_temporal=False:
        conv1: W/2, maxpool: W/2, layer2: W/2 → total W/8
        So width_downsample should be 8. Code says 8. CORRECT.
      
VERDICT: NOT a bug. The dimensions check out. Conv2d(2,1) is safe.

BUG #2 — SEVERE (SILENTLY DESTROYS ACCURACY)
File: src/transforms.py, lines 146-148
What: scaled_w is captured AFTER rotation and perspective transforms.
      Rotation with fill=255 EXPANDS the image before resize.
      BUT the real problem is this sequence:
        1. Grayscale
        2. Elastic distort (changes pixel VALUES, not size)
        3. Morphological ops (changes pixel VALUES, not size)
        4. Rotation (with fill=255 — PIL auto-expands canvas)
        5. Perspective (with fill=255 — PIL auto-expands canvas)
        6. _resize_keep_aspect → scaled_w captured HERE
        7. _pad_to_width
      
      After rotation, the PIL image may be LARGER than the original.
      Then _resize_keep_aspect uses target_h/h as the scale factor.
      The rotated image has a larger h, so scale = target_h / larger_h
      which means scale is SMALLER, so the final width is SMALLER.
      This means scaled_w will be SMALLER than expected for rotated images.
      
      The padding mask will then mask out LESS of the padded region,
      causing the Transformer attention to attend to some white padding,
      which adds noise to features.

      This is a MINOR accuracy issue, not a crash. The effect is small
      because rotation is only ±5° and perspective jitter is 5%.

VERDICT: MINOR accuracy issue. scaled_w is slightly wrong for augmented
         images. Not worth fixing — the error is small and it only affects
         training images (val/test transforms have no augmentation).

BUG #3 — SEVERE (SILENTLY DESTROYS ACCURACY)
File: src/models/ar_model.py, lines 237-239
What: The CTC head receives memory from the Transformer Encoder, but the
      CTC loss uses blank=0 as the blank token. The PAD token is also 0.
      
      In the CTC target construction (lines 244-249):
        valid_tokens = labels[i, 1:llen-1]
      
      This extracts tokens between SOS and EOS. If ANY actual Telugu 
      character in the vocabulary has id=0, it would be treated as blank
      and swallowed by CTC.
      
      Checking vocab.py: PAD=0, SOS=1, EOS=2, UNK=3, then Telugu chars
      start at index 4+. So NO Telugu character has id=0.
      
      Also: the CTC targets should NEVER contain the blank token (0).
      Since valid_tokens excludes SOS(1) and EOS(2), and PAD(0) only
      appears after EOS in the padded region, valid_tokens will never
      contain 0.

VERDICT: NOT a bug. CTC blank=0 and PAD=0 overlap is safe because
         CTC targets never contain PAD.

BUG #6 — SEVERE (SILENTLY DESTROYS ACCURACY)  *** REAL BUG ***
File: src/models/ar_model.py, lines 263-266
What: CTC Loss input/target length mismatch risk.
      
      The CTC loss requires: output_lens[i] >= ctc_label_lens[i]
      for every sample in the batch. If any label is LONGER than the
      encoder output sequence, CTC will produce inf/NaN loss.
      
      The encoder output sequence length = input_width // 8 (default).
      For a very narrow image (e.g., a single character, width=40px):
        encoder_seq = 40 // 8 = 5 time steps
      If the label has 6+ characters, CTC cannot align them to 5 steps.
      
      The code uses zero_infinity=True which will turn inf→0, preventing
      NaN gradients. But those samples will contribute ZERO to the CTC
      loss, meaning the CTC head learns NOTHING from short-width images.
      This silently degrades the CTC auxiliary signal.
      
      How common is this? Telugu words are typically 3-8 characters.
      With max_label_len=32, labels up to 32 chars exist.
      For a 64px-wide image (after aspect ratio resize): 
        encoder_seq = 64 // 8 = 8
      A 32-char label needs at least 32 time steps. This WILL fail.

VERDICT: REAL BUG but mitigated by zero_infinity=True. The CTC loss
         silently ignores samples where label is longer than encoder seq.
         This is a known CTC limitation and is acceptable given the
         auxiliary nature of this head. No fix needed if you accept this.

BUG #7 — SEVERE (SILENTLY DESTROYS ACCURACY)  *** REAL BUG ***
File: src/models/ar_model.py, line 239
What: log_probs = ctc_logits.log_softmax(dim=-1).permute(1, 0, 2)
      
      The permute(1, 0, 2) converts [B, T, C] → [T, B, C].
      This is correct for PyTorch's CTCLoss which expects [T, B, C].
      
      BUT: the CTC head operates on the Transformer Encoder memory.
      If the Transformer Encoder uses memory_key_padding_mask, the 
      encoder output at padded positions may contain GARBAGE values
      (the encoder doesn't zero them out — it just masks attention).
      
      These garbage values flow into ctc_head → log_softmax → CTC loss.
      However, output_lens correctly limits CTC to only use valid timesteps,
      so the garbage values in padded positions are ignored by CTCLoss.

VERDICT: NOT a bug. CTC output_lens correctly handles this.

BUG #9 — MODERATE (REDUCES ACCURACY)  *** REAL BUG ***
File: src/train_ar.py, lines 249-253
What: When constrain_decode=True in config, the validation runs TWICE:
        1. Once with constraints (for logging)
        2. Once without constraints (for checkpoint selection)
      
      This means validation takes 2x the time it should. Not a bug per se,
      but it doubles the validation time every epoch.
      
      More importantly: the constrained CER is logged to TensorBoard with
      the SAME key "val/CER" as the unconstrained CER. Both calls to
      validate() write to "val/CER", so TensorBoard will show TWO points
      per epoch, and the second one (unconstrained) will overwrite the first.

VERDICT: REAL BUG — TensorBoard metric collision. The constrained and
         unconstrained CER are logged with the same key. Should use 
         different keys like "val/CER_constrained" vs "val/CER".

BUG #10 — MODERATE (REDUCES ACCURACY)  *** REAL BUG ***
File: src/vocab.py, lines 243-257
What: The transition matrix is built using raw label text WITHOUT NFC 
      normalization. If the training labels contain decomposed Unicode
      (NFD), the bigrams observed will be between decomposed characters.
      But the model's predictions (after NFC normalization) may produce
      COMPOSED characters. This means the constraint matrix might block
      valid transitions that only exist in the NFC form but not in the
      raw label form.
      
      Example: A label might contain "క" + "్" + "ర" (3 codepoints, NFD).
      NFC might compose this into a single precomposed character.
      The bigram (క, ్) is recorded, but if NFC produces a different
      codepoint, the constraint matrix won't have seen it.

VERDICT: REAL BUG — could block valid transitions during constrained
         decoding. Should apply NFC normalization to labels BEFORE
         building the transition matrix.

BUG #11 — MODERATE  *** REAL BUG ***
File: src/transforms.py, lines 151-157
What: The random perspective transform generates BOTH startpoints AND 
      endpoints randomly. This means the transform is essentially random
      noise rather than a controlled perspective warp.
      
      Correct usage: startpoints should be the CORNERS of the original 
      image, and endpoints should be the jittered corners. Currently both
      are randomly jittered, which produces unpredictable (and often 
      identity-like) transforms.

VERDICT: REAL BUG — the perspective augmentation is nearly useless.
         startpoints should be the actual image corners.
